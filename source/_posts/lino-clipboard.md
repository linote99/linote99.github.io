# Lino 剪贴板同步：让 UFI 的剪贴板和网页双向打通

UFI 放在角落当热点用，平时不怎么碰它。但总有需要往它里面填东西的时候——比如在某台设备上收了个验证码、复制了一段网址，想把内容弄到 UFI 上粘贴。这时要么把 UFI 拿过来操作，要么用 ttyd 进去敲命令，都不顺手。

反过来也一样：UFI 上看到的内容（比如终端里的报错、短信里的验证码）想弄到电脑上，得手抄或者截图。

这个插件把两边打通了：在高级后台的网页里直接读写 UFI 的系统剪贴板，还带一份跨端共享的历史。

## 先说结论：纯前端做不到

最直觉的做法是在网页里用 `navigator.clipboard`。但这里行不通，原因在 Android 系统层。

`ClipboardService.clipboardAccessAllowed()` 对「读」剪贴板要求调用方满足三者之一：

| 条件 | 网页所在应用在后台时 |
|---|---|
| 持有签名级权限 `READ_CLIPBOARD_IN_BACKGROUND` | ✗ |
| 是当前默认输入法 | ✗ |
| 当前拥有窗口焦点 | ✗ |

三条全不满足。网页拿到的永远是 `null`，也收不到剪贴板变化事件。

所以这个插件不是纯 JS，而是 **JS + 一个很小的设备端工具**。插件本体里以 base64 内嵌着一份 14.5 KB 的 dex，首次使用时自动落到设备的 `/data/local/tmp/`，不装 APK、不加 Magisk 模块、不注册任何系统组件。

## 突破口：com.android.shell 有这个权限

翻 AOSP 源码时注意到一件事：`com.android.shell`（uid 2000）**持有** `READ_CLIPBOARD_IN_BACKGROUND`。

于是思路就有了：让设备端工具以 uid 2000 的身份调用 `IClipboard`，把 `callingPackage` 参数传成 `com.android.shell`。这样权限校验的第一条就满足了，无需焦点也能读写。

实测这条路是通的：

- 写入后由另一个进程读取，内容还在
- 进程退出后内容不丢（由 `system_server` 持有）
- 剪贴板变化回调也能正常收到

有个细节必须处理：**用 root 身份反而不行**。`AppOpsManager.checkPackage(0, "com.android.shell")` 会因为「包不属于该 uid」抛 `SecurityException`。所以工具被 root 调起时，会先自己降权到 uid 2000 再操作剪贴板。

降权用的是 `android.system.Os.setuid()`。这里不能反射 `android.os.Process.setuid()`——后者在 Android 11+ 属于 non-SDK 接口，实测直接 `NoSuchMethodException`。

## 三个踩过的坑

### 1. ClipboardManager 会静默失败

第一版用的是标准 API `ClipboardManager.setPrimaryClip()`。结果写入不生效、读取返回 `null`，**而且不抛任何异常**。

原因还是那个：`opPackageName` 与 uid 不匹配时，系统不会报错，只是什么都不做。这种失败极难排查，因为没有错误可看。

最后改成直连 `IClipboard` AIDL，写入后立刻回读校验——不回读就发现不了这种静默失败。

### 2. root 身份用不了，必须降权

上面说过了。这个坑的隐蔽之处在于：如果不降权，报的是 `SecurityException`，容易被误判成「权限不够，需要更高权限」，从而往错误的方向找解决方案。

### 3. 同一次复制会触发两次回调

系统的 `dispatchPrimaryClipChanged` 对一次复制会连发两次（`setPrimaryClip` 一次 + 文本分类广播一次），而且这两次事务可能落在**不同的 binder 线程**上并发执行。

不加锁的话，「比较上次内容」和「写入历史」之间会被插队，导致同一条内容被记两遍。加了锁并用 1.5 秒窗口去重才稳定。

还有一个更隐蔽的：如果同时跑着两个监听进程，它们会往同一个历史文件重复写。所以监听启动时会扫 `/proc` 做进程级单例校验，不只看 pidfile——pidfile 会被后来者覆盖。

## 功能

装好后主页会多一个「剪贴板同步」折叠栏，分三块。面板上不放说明文字，功能介绍收在「使用说明」按钮里。

### 写入设备剪贴板

- **写入设备剪贴板**：把输入框内容写进 UFI 的系统剪贴板，之后在设备上任何能粘贴的地方都能用
- **读取当前剪贴板**：把设备当前剪贴板内容读出来填进输入框
- **开启后台监听**：见下节

### 剪贴板历史

历史存在设备文件 `/data/local/tmp/lino_clipboard/history.jsonl`，每行一条 JSON。**任何浏览器打开高级后台看到的都是同一份**，换台电脑也能看到之前的内容。

历史区顶部有「刷新历史」和「清空历史」（清空需连点 3 次确认）。每条历史右侧有三个按钮：

| 按钮 | 作用 |
|---|---|
| 写入 | 写到 ufi 设备剪贴板 |
| 复制 | 复制到当前浏览器的剪贴板（你正在用的电脑） |
| 删除 | 只删这一条 |

「写入」和「复制」方向相反，容易搞混，所以界面上把名字分开了。

### 设置

安装设备端工具、开机自启、卸载，以及「使用说明」。安装状态由按钮文字体现（未安装时显示「安装设备端工具」，装好后变「已安装」）。

## 后台监听是干嘛的

一个常驻在设备上的进程，向系统剪贴板服务注册变化回调。

| 状态 | 历史来源 |
|---|---|
| 未开启 | 只有你在插件里点「写入」的记录 |
| 已开启 | 插件写入 **+ 设备上其它应用复制的内容** |

也就是说，想在历史里看到「我在 UFI 上复制的验证码」，必须开这个。不开就抓不到设备本机的复制行为。

为什么必须常驻：剪贴板变化回调只发给**还活着且已注册**的进程。每次都临时起一个进程是收不到的——事件发生时它不在。

开启后重启设备会丢，除非同时开了「开机自启」（写进 `/sdcard/ufi_tools_boot.sh`）。

## 适用范围与限制

在 ZTE U30 Air（Android 13，UFI-TOOLS 4.1.5）上实测通过：

- 写入含中文与 emoji 的文本，回读一致
- 9000 字长文本写入正常
- 另一个进程写入剪贴板（等价于用户在其他 App 里复制）能被监听捕获
- 真实重启设备后，开机自启成功拉起监听

已知限制：

- **只同步文本**。复制图片、文件时回调也会触发，但读不到文本就跳过，不记录
- 设备端工具依赖 `/data/local/tmp` 可写。被系统清理后点一次「安装设备端工具」即可恢复
- 面板不做自动轮询（每次设备操作都是一次 HTTP 往返），改成「展开时拉一次 + 手动刷新 + 写入后回读」
- 「复制」依赖浏览器剪贴板权限。http 非安全上下文下 `navigator.clipboard` 不可用，已用 `execCommand` 兜底，仍失败会提示手动选中复制
